スクリプト販売とリーク対策

結論

このレッスンを終えると、自分が開発したスクリプトを販売する際に、Cfx.re公式の「Asset Escrow」でコード自体を保護しつつ、自前のライセンスキー認証を組み合わせて、無断リーク・購入者以外での不正利用のリスクを抑える設計ができるようになります。「絶対に漏れない」保護は存在しませんが、市販されている多くのFiveMスクリプトが実際に採用している考え方を扱います。

説明

スクリプトの保護は、役割が異なる2つの仕組みを組み合わせて考えます。①Cfx.re公式のAsset Escrow: Luaコード自体をCfxのサーバー上で暗号化し、権限のあるサーバーでしか実行できないようにする、プラットフォーム側の保護。②自前のライセンス認証: 自分で用意したライセンスサーバーに問い合わせ、正規に購入されたキーかどうかをresource起動時に確認する、開発者側で組み込む保護。Escrowは強力ですがNUI(HTML/CSS/JS)ファイルは保護対象外という制限があるため、NUIを多用するスクリプトほど②の考え方や、そもそもNUI側に重要なロジックを置かない設計(Tier3-05のサーバー権威の原則)が重要になります。

コード例

① Asset Escrowの有効化(docs.fivem.netで確認済み)

fxmanifest.luaに特別な記述は不要で、Cfxポータル(portal.cfx.re)で「Create an asset」からzipをアップロードすると自動的にLua/YFT/YDD/YDRファイルが暗号化されます。設定ファイルなど、あえて暗号化したくないファイルだけ除外することもできます。

-- fxmanifest.lua
-- config.luaだけはEscrowの対象から除外し、平文のまま配布したい場合
escrow_ignore {
    'config.lua'
}

② 自前のライセンスキー認証(設計パターン)

Tebex経由でEscrow配布する以外のチャネル(自社サイト・Discord経由の直接販売など)で配布する場合や、Escrowを補完したい場合は、購入者ごとに発行したライセンスキーを、自分で用意したライセンスサーバーに問い合わせて確認する仕組みを自作します。以下は考え方を示す設計パターンです(https://license.example.com/api/verifyの部分は自分で用意するAPIに置き換えてください)。

-- server.lua
local LICENSE_API = 'https://license.example.com/api/verify' -- 自分で用意するライセンスサーバー
local MY_LICENSE_KEY = 'CHANGE-THIS-TO-THE-KEY-ISSUED-TO-THE-BUYER'
local isLicensed = false

CreateThread(function()
    local serverLicenseKey = GetConvar('sv_licenseKey', '') -- そのFXServer固有のキー(Tier1-14参照)

    PerformHttpRequest(LICENSE_API, function(statusCode, response)
        if statusCode == 200 then
            local data = json.decode(response)
            if data and data.valid then
                isLicensed = true
                print('^2[MyScript] ライセンス認証に成功しました^0')
                return
            end
        end
        print('^1[MyScript] ライセンス認証に失敗しました。主要機能を無効化します^0')
    end, 'POST', json.encode({
        licenseKey = MY_LICENSE_KEY,
        serverLicenseKey = serverLicenseKey, -- サーバー固有のキーも一緒に送り、1ライセンス=1サーバーに紐付ける
    }), { ['Content-Type'] = 'application/json' })
end)

-- 主要機能はisLicensedを確認してから動かす
RegisterNetEvent('myscript:mainFeature')
AddEventHandler('myscript:mainFeature', function()
    if not isLicensed then return end
    -- 本来の処理
end)

③ 買い手を特定できる「透かし」を仕込む

技術的に完全な防止が難しい以上、「漏れた場合にどこから漏れたか追跡できる」ことも抑止力になります。config内の識別子や、DBに保存するライセンスキーを購入者ごとに変えておくと、リークされたコピーからどの購入者経由か推測しやすくなります。

-- config.lua(購入者ごとに配布時に書き換えて渡す)
Config.LicensedTo = 'purchase_a1b2c3d4' -- 購入者ごとに異なる識別子(サポート対応・リーク時の追跡に使う)

注意点・よくあるミス

  • NUIファイルはEscrow対象外です。 価格計算やチート判定のような重要なロジックをNUI側のJavaScriptに書いてしまうと、Escrowを使っていてもそこだけ平文で読めてしまいます。重要な判定は必ずLua(server側)に置いてください。
  • 自前のライセンス認証は、ライセンスサーバー自体が落ちている間、正規購入者まで機能が止まってしまうリスクがあります。タイムアウト処理や、一定期間はキャッシュされた認証結果で動かす猶予期間を設けるなどの配慮を検討してください。
  • 過度に複雑な難読化やアンチデバッグ処理は、正規購入者の環境でも誤動作(false positive)を起こしやすく、サポート対応の負担やレビュー評価の低下につながりがちです。保護の強さと運用のしやすさのバランスを考えましょう。
  • 技術的な保護だけで100%は防げません。利用規約(再配布禁止・購入者本人のみ利用可等)を明記し、技術的対策と合わせて運用することが実務上は一般的です。

補足

Tebex経由での配布であれば、Escrowと購入・配布の導線が公式に統合されているため、まずはこの仕組みを検討するのが最も確実です(Tier4-39のTebex連携も参照)。独自のライセンス認証は、Tebex以外のチャネルで配布する場合や、Escrowでは保護できないNUI部分を補完したい場合の選択肢として位置づけてください。いずれの方法も、Tier5-04で学んだ「サーバー権威設計の徹底」が土台になっている点は変わりません。

Asset Escrowの対応ファイル種別・制限事項は将来変わる可能性があります。本レッスンの内容はdocs.fivem.netの公式ドキュメントで確認済みですが、実際に販売する際は最新の公式ドキュメントも必ず確認してください。
