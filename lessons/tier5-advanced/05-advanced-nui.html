高度なNUI(React等の活用)

結論

このレッスンを終えると、Vite等のビルドツールを使ったReactベースのNUI構築の考え方と、このサイトのようなビルドレス構成との違い・使い分けを理解できるようになります。

説明

Tier3〜4で作ったNUIは、素のHTML/CSS/JSファイルをそのままui_pageに指定するシンプルな構成でした。画面が小さく、状態管理も単純なうちはこれで十分です。

しかし、インベントリ画面やダッシュボードのように状態(表示するデータ)が複雑で、頻繁に更新される画面を作る場合、React/Vue等のUIライブラリと、Vite等のビルドツールを組み合わせて開発する方が生産性が高くなります。この場合、開発時はnpm run dev等でホットリロードしながら作り、最終的にnpm run buildでHTML/CSS/JSの静的ファイル一式に変換してからui_pageに指定します。

コード例

ビルドツールを使う場合のディレクトリ構成イメージ

my-resource/
├── fxmanifest.lua
├── client.lua
├── server.lua
├── ui/                  # Reactプロジェクトのソース
│   ├── src/
│   │   ├── App.jsx
│   │   └── main.jsx
│   ├── package.json
│   └── vite.config.js
└── ui-build/            # `npm run build` で生成される静的ファイル(これをui_pageに指定)
    ├── index.html
    └── assets/
        ├── index.js
        └── index.css

fxmanifest.lua: ビルド後の成果物を指定する

ui_page 'ui-build/index.html'

files {
    'ui-build/index.html',
    'ui-build/assets/*.js',
    'ui-build/assets/*.css'
}

React側でLuaからのメッセージを受け取る例

import { useEffect, useState } from 'react';

function App() {
  const [balance, setBalance] = useState(0);

  useEffect(() => {
    function handleMessage(event) {
      if (event.data.action === 'updateBalance') {
        setBalance(event.data.balance);
      }
    }
    window.addEventListener('message', handleMessage);
    return () => window.removeEventListener('message', handleMessage);
  }, []);

  return 
残高: {balance}円
;
}

export default App;

注意点・よくあるミス

  • ui_pageにはビルド後の静的ファイル(ui-build/index.html等)を指定します。ソースのui/src/App.jsxを直接指定しても、ブラウザ(CEF)はJSXをそのまま実行できないため動きません。
  • npm run buildを実行し忘れたまま古いui-buildのファイルをコミット・配布してしまうと、変更が反映されません。デプロイ前に必ずビルドし直す運用(CI等での自動化も検討)が必要です。
  • Lua⇔JS間のメッセージのやり取り自体(SendNUIMessage/window.addEventListener('message', ...)/fetchによるRegisterNUICallback呼び出し)は、ビルドツールを使っても使わなくても同じ仕組みです。フロントエンドの実装方法が変わるだけで、通信の考え方はTier3で学んだものと変わりません。

補足

このFiveMスクリプト学習サイト自体は、あえてビルドツールなしの素のHTML/CSS/JSで作られています(CLAUDE.md参照)。理由は「Claude Codeが1ファイルずつ確実に生成・検証できる」「ユーザーがnpm install不要でそのままブラウザ・GitHub Pagesで確認できる」ためです。画面数が少なく状態もシンプルなプロジェクトではビルドレス構成が有利ですが、NUIのように状態管理が複雑になりがちな画面では、ビルドツールを使う設計が有利になる場合が多い、というのがこのレッスンの結論です。プロジェクトの規模・複雑さに応じて、両方の選択肢を検討できるようになりましょう。
