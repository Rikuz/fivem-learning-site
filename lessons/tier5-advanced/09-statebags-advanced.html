StateBagsの応用パターン

結論

このレッスンを終えると、StateBags(Tier5-03)に複雑なデータを持たせる際の設計、変更検知の絞り込み、ルーティングバケットとの併用といった、実運用でよく使われる応用パターンを実装できるようになります。

こんな時に使う: 複数の値をまとめて1つのStateBagキーで管理したい、特定の値の変化だけを効率よく検知したいとき。

説明

Tier5-03では単一の値(job等)をStateBagに設定する例を扱いました。実運用では、複数の関連する値をまとめてテーブルとして持たせたり、特定のキーの変化だけをclient側で監視したりする場面が多くあります。

コード例

複数の値をまとめたテーブルを持たせる

-- server.lua
Player(playerId).state:set('status', {
    hunger = 80,
    thirst = 60,
    stamina = 100,
}, true)

特定のキーの変化だけを監視する(第2引数でキーを絞り込む)

-- client.lua
-- 第2引数を空文字列 '' にすると全エンティティのstatusの変化を監視する
AddStateBagChangeHandler('status', '', function(bagName, key, value, reserved, replicated)
    if value.hunger < 20 then
        print(bagName .. 'の空腹度が低下しています')
    end
end)

-- 特定のプレイヤーのbagNameだけを対象にしたい場合は、bagNameを直接指定する
-- 例: AddStateBagChangeHandler('status', ('player:%s'):format(playerId), handler)

ルーティングバケット(Tier5-08)と組み合わせる

-- 強盗インスタンス内だけで共有したい進行状況をStateBagsで管理する
Entity(heistDoor).state:set('isBreached', false, true)

AddStateBagChangeHandler('isBreached', '', function(bagName, key, value)
    if value == true then
        print('ドアが突破されました')
    end
end)

ルーティングバケットが分かれていても、StateBagの変更通知はバケットの境界を越えて届く場合があるため、本当にそのインスタンス内だけで完結させたい情報は、バケットIDを含めたキー設計(例: heist_100_doorState)にするなどの工夫が必要になることがあります。

注意点・よくあるミス

  • StateBagに大きなテーブルを頻繁にsetすると、その都度シリアライズ(データを送信用の形式に変換する処理)とネットワーク送信が発生し、負荷が高くなります。変化の少ない値をまとめる、更新頻度を抑えるといった工夫をしましょう(Tier5-01のパフォーマンス計測と組み合わせて確認するのがおすすめです)。
  • AddStateBagChangeHandlerのハンドラは、そのキーが変化するたびに呼ばれます。ハンドラの中で重い処理をすると、変化のたびに負荷がかかるため、最小限の処理にとどめてください。
  • 複数のresourceが同じStateBagキーに書き込むと、お互いの値を上書きし合ってしまいます。キー名の命名規則(resource名を含める等)を決めておくと衝突を防げます。

補足

StateBagsは便利ですが万能ではありません。「多くのclientが継続的に参照する、比較的静的なデータ」に向いており、高頻度で細かく変わる座標などのデータには、既存のネイティブな同期機構を使う方が適しています(Tier5-03の補足も参照してください)。
