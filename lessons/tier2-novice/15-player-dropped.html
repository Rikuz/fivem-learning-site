切断理由の取得と後処理

結論

このレッスンを終えると、プレイヤーがサーバーから切断したタイミングを検知し、切断理由を取得しつつ後片付け処理を行うことができるようになります。

こんな時に使う: 切断時にプレイヤーのデータを保存したい、切断ログを記録したい、切断時にNPC・車両などそのプレイヤーが生成したものを片付けたいとき。

説明

playerDroppedは、プレイヤーがサーバーから切断されたとき(自主的な退出、キック、タイムアウト等)にserver側で発火するイベントです。切断されたプレイヤーのsourceはまだこのイベント内でのみ有効なので、必要な情報はこのタイミングで取得しておく必要があります。

コード例

server.lua: 切断理由を取得してログに残す

AddEventHandler('playerDropped', function(reason)
    local playerId = source
    local playerName = GetPlayerName(playerId)

    print(('プレイヤー%s(%s)が切断しました。理由: %s'):format(playerName, playerId, reason))
end)

切断時にデータを保存する

AddEventHandler('playerDropped', function(reason)
    local playerId = source
    local identifier = GetPlayerIdentifiers(playerId)[1]

    -- Tier3-15「プレイヤーデータの自動保存設計」と組み合わせる想定
    saveInventory(identifier, playerId) -- Tier3-04で作った保存関数の例

    -- メモリ上のデータをクリーンアップする(Tier3-04のinventoriesテーブル等)
    inventories[playerId] = nil
end)

切断理由の主なパターン

AddEventHandler('playerDropped', function(reason)
    if reason:find('Timed out') then
        print('タイムアウトによる切断')
    elseif reason:find('kicked') then
        print('キックによる切断')
    else
        print('自主的な切断、またはその他の理由: ' .. reason)
    end
end)

注意点・よくあるミス

  • playerDroppedのイベントハンドラの中では、既にそのプレイヤーとの接続が切れかけています。TriggerClientEventで何かを送っても届きません。
  • データ保存処理に時間がかかる非同期処理(DB書き込み等)を行う場合、処理が完了する前にresourceが再起動されるとデータが失われる可能性があります。重要なデータは定期オートセーブ(Tier3-15)と組み合わせて、切断時保存だけに頼らない設計が安全です。
  • reasonの文字列の形式はFiveMのバージョンによって変わることがあります。正確な分類が必要な場合は、部分一致(string.find)ではなく、公式ドキュメントで案内されている判定方法も確認してください。

補足

似たイベントにplayerConnecting(接続開始時、Tier4-07で扱った)、playerJoining(参加処理中)があります。「接続」「参加完了」「切断」という3つのタイミングを意識して設計すると、プレイヤーのセッション管理が整理しやすくなります。
