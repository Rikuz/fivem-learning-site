ホワイトリスト・応募フォームシステム

結論

このレッスンを終えると、許可されたプレイヤーだけがサーバーに参加できるホワイトリスト機能を実装できるようになります。

こんな時に使う: 身内サーバーで知り合いだけ参加させたい、審査制のRPサーバーで応募・承認された人だけ入れるようにしたいとき。

説明

playerConnectingイベントは、プレイヤーが接続してきた瞬間にserver側で発火します。deferrals(接続処理を保留し、DB確認などの非同期処理を待ってから許可/拒否を決める仕組み)と組み合わせることで、ホワイトリストチェック(許可リストに載っているかどうかの確認)ができます。同じ仕組みはTier4-07「BAN・キック機能を実装する」でも登場します(あちらは「載っていたら拒否」、こちらは「載っていなければ拒否」という逆方向の判定です)。

コード例

server.lua: ホワイトリストにない接続を拒否する

AddEventHandler('playerConnecting', function(playerName, setKickReason, deferrals)
    deferrals.defer()
    Wait(0)

    local source = source
    local license = nil
    for _, id in ipairs(GetPlayerIdentifiers(source)) do
        if id:find('license:') then license = id end
    end

    MySQL.Async.fetchAll('SELECT * FROM whitelist WHERE identifier = @id AND approved = 1', {
        ['@id'] = license
    }, function(result)
        if result and result[1] then
            deferrals.done() -- ホワイトリストに載っていれば許可
        else
            deferrals.done('このサーバーはホワイトリスト制です。応募フォームから申請してください: https://example.com/apply')
        end
    end)
end)

応募フォームからの申請を受け付ける(外部フォーム連携の例)

実運用では、応募フォーム自体はDiscordのフォームBotやWebフォームなどサーバー外の仕組みで受け付け、承認されたら管理者が以下のようなコマンドでDBに登録する、という運用が一般的です。

RegisterCommand('approve', function(source, args)
    if not IsPlayerAceAllowed(source, 'command.approve') then return end

    local licenseId = args[1]
    MySQL.Async.execute('INSERT INTO whitelist (identifier, approved) VALUES (@id, 1)', {
        ['@id'] = licenseId
    })
end, false)

注意点・よくあるミス

  • Tier4-07のBANチェックと同様、deferrals.done()を必ずどこかの分岐で呼んでください。呼び忘れると接続処理が止まったままになります。
  • ホワイトリストとBANの両方を実装する場合、判定の順序(先にBANを確認してから、次にホワイトリストを確認する等)を明確にしておかないと、意図しない挙動になることがあります。
  • 「サーバー管理者がDBに直接手動でINSERTする」運用は小規模なら現実的ですが、応募人数が増えると管理者用のNUI(Tier3-20「管理者メニューの基礎設計」)から操作できるようにする方が安全で楽になります。

補足

応募フォーム自体をNUIやDiscord Bot連携(Tier4-13)で自動化することもできますが、まずは「DBにホワイトリストのテーブルがあり、それをチェックする」という核となる部分を理解することが重要です。
