JSON保存 vs リレーショナル設計の使い分け

結論

このレッスンを終えると、データを1つのJSON列にまとめて保存する方法と、複数のテーブルに分けて保存する方法(正規化)のメリット・デメリットを理解し、状況に応じて選べるようになります。

こんな時に使う: Tier3-04のインベントリのようなデータをDBに保存する際、「1列にまとめるか、テーブルを分けるか」で迷ったとき。

説明

Tier3-04では、インベントリをjson.encodeで1つの文字列にしてusersテーブルの1列に保存する方法を扱いました。これは手軽ですが、常に最適とは限りません。テーブルを分けて1アイテム1行で保存する正規化(データの重複や矛盾を防ぐためにテーブルを分割する設計手法)という選択肢もあります。

コード例

方式A: JSON列にまとめる

-- テーブル: users (identifier, name, inventory)
-- inventory列には '{"water":3,"bread":1}' のようなJSON文字列が入る

MySQL.Async.execute('UPDATE users SET inventory = @inventory WHERE identifier = @id', {
    ['@inventory'] = json.encode({ water = 3, bread = 1 }),
    ['@id'] = identifier
})

方式B: テーブルを分ける(正規化)

-- inventory_items テーブル(1アイテム1行)
-- identifier | item_name | amount
-- "abc123"   | "water"   | 3
-- "abc123"   | "bread"   | 1
-- アイテムを1件だけ更新する場合、方式Bなら該当行だけ更新すればよい
MySQL.Async.execute('UPDATE inventory_items SET amount = @amount WHERE identifier = @id AND item_name = @item', {
    ['@amount'] = 5,
    ['@id'] = identifier,
    ['@item'] = 'water'
})

注意点・よくあるミス

  • 方式A(JSON)の弱点: 「アイテムを1件だけ検索・集計する」ようなSQL(「waterを100個以上持っているプレイヤーを探す」等)がとても書きにくくなります。全プレイヤーのJSONを読み込んでLua側で判定する必要が出てくることがあります。
  • 方式B(正規化)の弱点: テーブル数が増え、DBスキーマの設計・マイグレーション(Tier4-08)の手間が増えます。単純なデータには過剰な設計になることもあります。
  • 「検索・集計したいか」「構造が固定的か」を基準に選ぶのが実用的な指針です。単純なユーザー設定はJSON、検索や在庫管理が絡むデータ(インベントリ、取引履歴等)はテーブル分割、という使い分けが一般的です。

補足

実際のox_inventory(Tier3-04)やokokBanking(Tier4-06)のような本格的なリソースは、検索・集計のしやすさを重視してテーブルを分ける正規化設計を採用しています。自作の小規模なスクリプトではJSON方式から始め、必要になったら正規化する、という段階的なアプローチも現実的です。
