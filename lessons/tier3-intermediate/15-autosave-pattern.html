プレイヤーデータの自動保存設計

結論

このレッスンを終えると、切断時の保存だけに頼らず、一定間隔でのオートセーブを組み合わせて、サーバークラッシュ時のデータ損失を減らす設計ができるようになります。

こんな時に使う: サーバーが不意に落ちても、プレイヤーの所持金やインベントリの変化がなるべく失われないようにしたいとき。

説明

Tier2-15で学んだplayerDroppedでの保存だけでは、サーバーが正常に切断処理を行えないまま落ちた場合(クラッシュ、強制終了)にデータが保存されません。これを補うため、全プレイヤーのデータを一定間隔で保存し続けるオートセーブループを用意するのが一般的です。

コード例

server.lua: 定期オートセーブループ

local function saveAllPlayers()
    for _, playerId in ipairs(GetPlayers()) do
        local identifier = GetPlayerIdentifiers(playerId)[1]
        saveInventory(identifier, tonumber(playerId)) -- Tier3-04で作った保存関数
    end
    print('全プレイヤーのデータをオートセーブしました')
end

CreateThread(function()
    while true do
        Wait(5 * 60 * 1000) -- 5分ごと
        saveAllPlayers()
    end
end)

切断時・resource停止時にも保存する(多重の保険)

AddEventHandler('playerDropped', function()
    local playerId = source
    local identifier = GetPlayerIdentifiers(playerId)[1]
    saveInventory(identifier, playerId)
end)

AddEventHandler('onResourceStop', function(resourceName)
    if resourceName ~= GetCurrentResourceName() then return end
    saveAllPlayers() -- resourceの手動再起動・停止時にも保存する
end)

注意点・よくあるミス

  • プレイヤー数が多いサーバーで全員分を同時に保存すると、一瞬DBへの問い合わせが集中します。Tier5-02の非同期処理パターンを使い、サーバー全体を止めないようにしてください。
  • オートセーブの間隔を短くしすぎると、それだけDBへの負荷が増えます。「どれくらいのデータ損失なら許容できるか」を基準に間隔を決めましょう(5〜10分程度が一般的です)。
  • onResourceStopのイベントハンドラでは、resourceNameが「今まさに停止しようとしているresourceの名前」なのか「他のresourceが停止した通知」なのかを、GetCurrentResourceName()との比較で必ず確認してください。

補足

本格的な運用では、オートセーブの実行ログをDiscord Webhook(Tier3-22)で監視用チャンネルに送り、「保存が正常に行われているか」を運用者が確認できるようにすることもあります。
