サーバー側バリデーション

結論

このレッスンを終えると、クライアントから送られてきた値を無条件に信用せず、サーバー側で必ず再チェックするという、FiveMスクリプトで最も重要なセキュリティの考え方を実践できるようになります。

説明

FiveMのclient側は、改造ツール(チートクライアント)によって自由に書き換えられる可能性があります。「client側で入力チェックしているから安全」という設計は成り立ちません。お金・アイテム・権限に関わる判定は、必ずserver側でもう一度行う必要があります。これを「サーバー権威(サーバーが最終的な正しさの基準を持つ)」という考え方と呼びます。

コード例

❌ 危険な例(clientの言い値をそのまま信用している)

-- ⚠️ 悪い例: clientが送ってきた金額をそのままDBに反映してしまっている
RegisterNetEvent('shop:buyItem')
AddEventHandler('shop:buyItem', function(itemName, price)
    local playerId = source
    -- price はclient側から送られてきた値 → 改ざんされていれば0円で買えてしまう
    removePlayerMoney(playerId, price)
    addItem(playerId, itemName, 1)
end)

✅ 安全な例(価格はサーバー側の定義を使う)

-- 商品の価格はサーバー側だけが知っているテーブルで管理する
local shopItems = {
    potion = { price = 50 },
    bread  = { price = 20 },
}

RegisterNetEvent('shop:buyItem')
AddEventHandler('shop:buyItem', function(itemName)
    local playerId = source
    local item = shopItems[itemName]

    -- 1. そもそも存在する商品名かチェックする
    if not item then
        print(('プレイヤー%sが不正な商品名を送信: %s'):format(playerId, tostring(itemName)))
        return
    end

    -- 2. 所持金が足りているかサーバー側のデータで確認する
    local currentMoney = getPlayerMoney(playerId)
    if currentMoney < item.price then
        TriggerClientEvent('myscript:notify', playerId, '所持金が足りません')
        return
    end

    -- 3. サーバー側で保持している価格だけを使って処理する(clientからの価格は一切使わない)
    removePlayerMoney(playerId, item.price)
    addItem(playerId, itemName, 1)
end)

注意点・よくあるミス

  • 「金額」「個数」「対象プレイヤーID」など、悪用されると被害が大きい値はclientから送らせず、server側の定義・DBの値だけを使うのが基本方針です。clientからは「商品名」のような”どれを選んだか”の情報だけを送ってもらいます。
  • 入力値の型チェックも忘れずに行いましょう。tonumber()で数値変換できない値が来た場合の処理(nilチェック)を書かないと、エラーで処理が止まってしまうことがあります。
  • 距離や座標に関するチェック(「その場所の近くにいるか」など)も、client側の自己申告ではなくGetEntityCoordsをserver側から取得するか、client側から送られた座標をteleportハック対策として上限距離でチェックするなど、サーバー側での検証を組み合わせてください。

補足

この考え方はTier5「セキュリティ強化(チート対策)」でさらに発展させます。「clientは常に嘘をつく可能性がある」という前提で設計する癖をつけておくと、後々のトラブルを大きく減らせます。
