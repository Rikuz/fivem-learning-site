複数resourceにまたがるプロジェクト構成のコツ

結論

このレッスンを終えると、1つの大きな機能を複数のresourceに分割し、依存関係を整理して破綻しにくいプロジェクト構成にすることができるようになります。

こんな時に使う: 「銀行」「インベントリ」「フレームワーク連携」のように性質の異なる機能を1つのresourceに詰め込みすぎて管理が大変になってきたとき。

説明

Tier2-19で学んだのは1つのresource内でのファイル分割でしたが、規模が大きくなるとresource自体を分けることも検討します。「core(基盤)」「UI」「機能A」「機能B」のように分け、Tier3-06で学んだexportsで連携させるのが一般的なパターンです。

コード例

分割例: ショップシステムの構成

resources/[local]/
├── myshop-core/       -- 商品定義・購入ロジック(サーバー権威の中心)
│   └── fxmanifest.lua    -- exportsでAPIを公開する
├── myshop-ui/          -- NUI画面(myshop-coreのexportsを呼んで使う)
│   └── fxmanifest.lua    -- dependency 'myshop-core'
└── myshop-target/      -- ox_target連携部分(店員NPCへのインタラクション追加)
    └── fxmanifest.lua    -- dependency 'myshop-core', dependency 'ox_target'

myshop-core: 他から呼ばれるAPIを整理して公開する

local function BuyItem(source, itemName)
    -- 購入処理の本体(Tier3-05のサーバー側バリデーションを含む)
    return true
end

exports('BuyItem', BuyItem)

myshop-ui: coreのexportsを呼ぶ

RegisterNUICallback('confirmPurchase', function(data, cb)
    local success = exports['myshop-core']:BuyItem(source, data.itemName)
    cb(success)
end)

注意点・よくあるミス

  • 分割しすぎると、resource間の起動順序(dependency)の管理が複雑になります。「本当に独立して差し替えたい/再利用したい単位か」を基準に分割してください。
  • 命名規則を決めておかないと、resourceが増えるほどどれが何のためのものか分かりにくくなります。プロジェクト名-機能名のような接頭辞を統一すると管理しやすくなります。
  • 複数resourceに分けると、1箇所の変更で複数のフォルダを触る必要が出てきます。Tier1-08で学んだGitで、プロジェクト全体を1つのリポジトリとして管理すると変更履歴を追いやすくなります。

補足

okokシリーズやox系リソースも、実際には「core」「UI」「連携用アドオン」のように複数のresourceに分かれていることが多く、この設計パターンの実例と言えます。
