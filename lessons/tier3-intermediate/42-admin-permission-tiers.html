管理者権限レベル(Permission Tier)の設計

結論

このレッスンを終えると、モデレーター/管理者/開発者のような多段階の権限レベルを、ACE権限のprincipal(所属グループ)の入れ子構造で表現することができるようになります。Tier3-20の管理者メニュー基礎を、より実運用に近い権限設計へ発展させます。

こんな時に使う: 「BAN機能はmoderator以上、DB直接操作はdeveloperのみ」のように、機能ごとに必要な権限レベルを分けたいとき。

説明

ACE権限は、principal(グループ)同士をadd_principalで親子関係にすることで、上位グループが下位グループの権限を自動的に引き継ぐ階層構造を作れます。「developerはadminの権限をすべて持ち、adminはmoderatorの権限をすべて持つ」という設計にしておけば、権限チェックのコード自体は「moderator以上か」を確認するだけで済みます。

コード例

server.cfg: 権限レベルを入れ子で定義する

# グループごとに機能を割り当てる
add_ace group.moderator command.spectate allow
add_ace group.moderator command.freeze allow

add_ace group.admin command.ban allow
add_ace group.admin command.kick allow

add_ace group.developer command.db_query allow

# developerはadminの権限を、adminはmoderatorの権限を引き継ぐ(入れ子構造)
add_principal group.developer group.admin
add_principal group.admin group.moderator

# 実際にプレイヤーへ権限グループを割り当てる例(identifierは各自の環境に合わせる)
add_principal identifier.license:1234567890abcdef group.developer

server.lua: 権限レベルを1つの関数にまとめて確認する

-- 権限レベルの優先順位を定義しておく(数値が大きいほど強い権限)
local PERMISSION_LEVELS = {
    moderator = 1,
    admin = 2,
    developer = 3,
}

local function getPermissionLevel(playerId)
    if IsPlayerAceAllowed(playerId, 'group.developer') then return PERMISSION_LEVELS.developer end
    if IsPlayerAceAllowed(playerId, 'group.admin') then return PERMISSION_LEVELS.admin end
    if IsPlayerAceAllowed(playerId, 'group.moderator') then return PERMISSION_LEVELS.moderator end
    return 0
end

local function hasPermission(playerId, requiredLevel)
    return getPermissionLevel(playerId) >= PERMISSION_LEVELS[requiredLevel]
end

-- 使用例: BAN機能はadmin以上のみ実行可能にする
RegisterCommand('banplayer', function(source, args)
    local playerId = source
    if not hasPermission(playerId, 'admin') then
        TriggerClientEvent('myscript:notify', playerId, '権限がありません', 'error')
        return
    end
    -- Tier4-07のBAN処理へ続く
end, false)

注意点・よくあるミス

  • ACE権限のadd_principalによる入れ子は1方向です。「developerはadminの権限を持つ」を実現するにはadd_principal group.developer group.adminのように、上位グループを下位グループに所属させる形で書きます(逆にすると意図通りに継承されません)。
  • 権限チェックは必ずserver側の関数(hasPermission)を経由してください。client側でボタンの表示/非表示を切り替えるだけでは、直接イベントを発火されて回避されます(Tier3-20と同じ注意点)。
  • 権限レベルの数値(PERMISSION_LEVELS)はコード内の定数として管理し、権限グループ名の変更に強い設計にしておきましょう。

補足

フレームワークによっては、ACE権限とは別にJobベースの権限管理(Discord連携のロール確認、Tier4-13参照)を組み合わせることもあります。次のレッスン(Tier3-43)では、この権限レベルを使ってオンラインプレイヤー一覧・スペクテイト機能を制限します。
