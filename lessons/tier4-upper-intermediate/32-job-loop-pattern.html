ジョブループの基本設計(受注→実行→納品→報酬)

結論

このレッスンを終えると、「仕事」を1つの状態遷移(受注→実行→納品→報酬)として設計する考え方が身につきます。デリバリー・トラッカー・タクシーなど、あらゆるジョブ系スクリプトに共通して使える核心パターンです。

こんな時に使う: Tier4-02でJobの確認方法は学んだが、「実際に1つの仕事をどう組み立てればいいか分からない」というとき。

説明

ジョブは複雑に見えますが、分解すると「①受注(仕事を開始する)」「②実行(目的地に向かう・作業する)」「③納品(成果物を渡す)」「④報酬(お金を受け取る)」という4つの状態を順番に進むだけです。各状態をプレイヤーごとのテーブルで管理し、今どの状態にいるかをserverが必ず把握しておくことで、「納品をスキップして報酬だけ受け取る」といった不正を防げます。

コード例

server.lua: ジョブの状態をプレイヤーごとに管理する

local activeJobs = {} -- playerId -> { state = 'idle'|'accepted'|'delivering'|'completed', startedAt }

RegisterNetEvent('deliveryjob:accept')
AddEventHandler('deliveryjob:accept', function()
    local playerId = source

    if activeJobs[playerId] and activeJobs[playerId].state ~= 'idle' then
        TriggerClientEvent('myscript:notify', playerId, '既に仕事を受注中です', 'error')
        return
    end

    activeJobs[playerId] = { state = 'accepted', startedAt = GetGameTimer() }
    TriggerClientEvent('deliveryjob:onAccepted', playerId)
end)

server.lua: 状態を確認しながら次の工程に進める

RegisterNetEvent('deliveryjob:startDelivering')
AddEventHandler('deliveryjob:startDelivering', function()
    local playerId = source
    local job = activeJobs[playerId]

    -- 「受注済み」の状態からしか「配達中」には進めない、というルールをserverが強制する
    if not job or job.state ~= 'accepted' then return end

    job.state = 'delivering'
    TriggerClientEvent('deliveryjob:onDeliveringStarted', playerId)
end)

RegisterNetEvent('deliveryjob:completeDelivery')
AddEventHandler('deliveryjob:completeDelivery', function()
    local playerId = source
    local job = activeJobs[playerId]

    if not job or job.state ~= 'delivering' then return end

    local payout = 150 -- 報酬額は必ずserver側の定数で決める(Tier3-05参照)
    addPlayerMoney(playerId, payout) -- Tier4-01のフレームワーク連携で実装する想定

    activeJobs[playerId] = nil -- 次の仕事をまた受注できるよう状態をリセットする
    TriggerClientEvent('myscript:notify', playerId, ('配達完了。報酬$%sを受け取りました'):format(payout), 'success')
end)

注意点・よくあるミス

  • 状態遷移(idle → accepted → delivering → completed)を必ずserver側のactiveJobsテーブルで管理し、client側の判断だけで報酬イベントを発火できるようにしないでください。改造クライアントで受注をスキップして報酬だけ得られてしまいます。
  • 各イベントハンドラの先頭で「今どの状態にいるか」を必ず確認し、想定外の状態からの遷移は無視してください(上記コード例のif not job or job.state ~= '...'がこれにあたります)。
  • activeJobsはメモリ上のテーブルのため、サーバー再起動で受注中の仕事が消えます。長時間かかるジョブを扱う場合はTier3-15のオートセーブパターンでDB保存も検討してください。

補足

この4状態パターンは、デリバリー以外にも「強盗ミッション」「クラフトの受注生産」など、あらゆる「一連の作業」の設計に応用できます。次のレッスン(Tier4-33)では、この仕事に「オンデューティ管理」と「専用車両の貸出」を組み合わせます。
