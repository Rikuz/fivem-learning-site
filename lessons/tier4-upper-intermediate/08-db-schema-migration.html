DBスキーマのバージョン管理・マイグレーション

結論

このレッスンを終えると、テーブル構造の変更を、既存のデータを壊さずに安全に反映するマイグレーション(DB構造の変更手順を記録・適用する仕組み)の考え方を実装できるようになります。

こんな時に使う: 開発を続けるうちに「usersテーブルに新しい列を追加したい」となったとき、複数のサーバー(開発用・本番用)でDB構造を揃えたいとき。

説明

Tier3-03で作ったusersテーブルのようなDB構造は、開発が進むにつれて列の追加・変更が必要になります。ALTER TABLEを思いつきで直接実行すると、「どのサーバーにどの変更を適用したか」が分からなくなりがちです。マイグレーションファイル(1つの変更を1つのSQLファイルとして順番に管理する仕組み)を使うと、この混乱を防げます。

コード例

マイグレーションファイルの構成例

migrations/
├── 001_create_users_table.sql
├── 002_add_inventory_column.sql
└── 003_add_last_login_column.sql

002_add_inventory_column.sql

-- 既にinventory列がある場合はエラーにならないよう、存在確認してから追加するのが安全
ALTER TABLE users ADD COLUMN IF NOT EXISTS inventory LONGTEXT DEFAULT NULL;

003_add_last_login_column.sql

ALTER TABLE users ADD COLUMN IF NOT EXISTS last_login DATETIME DEFAULT NULL;

適用済みのマイグレーションを記録するテーブル

CREATE TABLE IF NOT EXISTS migrations (
    filename VARCHAR(255) PRIMARY KEY,
    applied_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

このテーブルに「どのマイグレーションファイルを適用済みか」を記録しておけば、新しいサーバーを立てたときや、他の開発者の環境でも、未適用のファイルだけを順番に実行すればDB構造を揃えられます。

注意点・よくあるミス

  • ALTER TABLEを本番DBに直接実行する前に、必ずバックアップを取ってください。列の削除・型変更は元に戻せない場合があります。
  • マイグレーションファイルは、番号順に1度だけ適用される前提で書きます。既に適用したファイルの中身を後から書き換えると、環境ごとにDB構造がずれる原因になります。修正したい場合は新しいマイグレーションファイルを追加してください。
  • データが既に入っているテーブルにNOT NULL制約付きの列を追加すると、既存の行に対してデフォルト値の指定が必要になる場合があります。DEFAULT句を忘れずに指定しましょう。

補足

大規模なチーム開発では、マイグレーション管理専用のツール(Node.jsのプロジェクトで使われるようなマイグレーションライブラリ)を導入することもありますが、個人〜小規模チームの開発では、この単純な連番SQLファイルの管理でも十分に効果があります。
