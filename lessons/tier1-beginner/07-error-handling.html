エラーハンドリング(pcall/xpcall)

結論

このレッスンを終えると、一部の処理でエラーが起きても、スクリプト全体・resource全体を止めずに安全に処理を継続することができるようになります。

こんな時に使う: 外部APIへの通信、DBの結果が想定と違う形で返ってきた場合、JSON文字列のパースなど「失敗する可能性がある処理」を実行するとき。

説明

通常、Luaの関数内でエラーが発生すると、そのエラーは呼び出し元に伝播し、対処しなければresource全体が止まってしまいます。pcall(protected call。関数を「保護された状態」で呼び出し、エラーが起きても落ちずに結果を返してくれる仕組み)を使うと、エラーを検知して自分で対処できます。

コード例

pcallの基本

local function riskyFunction()
    error('何か問題が発生しました') -- 意図的にエラーを発生させる
end

local success, errorMessage = pcall(riskyFunction)

if success then
    print('正常に完了しました')
else
    print('エラーが発生しました: ' .. errorMessage)
end

JSONパースなど、失敗しうる処理での活用

local function safeJsonDecode(jsonString)
    local success, result = pcall(json.decode, jsonString)

    if success then
        return result
    else
        print('JSONの解析に失敗しました: ' .. tostring(jsonString))
        return nil
    end
end

local data = safeJsonDecode('{invalid json')
print(data) -- nil(エラーにならず安全に処理が続く)

xpcall: エラー内容をより詳しく扱いたい場合

local function errorHandler(err)
    return debug.traceback(err, 2) -- スタックトレース(呼び出し履歴)付きのエラー情報を作る
end

local success, result = xpcall(riskyFunction, errorHandler)

if not success then
    print('詳細なエラー情報:')
    print(result)
end

注意点・よくあるミス

  • pcallは「起きる可能性のある異常」を扱うためのものです。プログラムのロジックの間違い(変数名のタイプミス等)までpcallで握りつぶしてしまうと、バグに気づきにくくなります。デバッグ中は積極的にエラーメッセージをprintで表示しましょう。
  • pcallで囲んだからといって、処理自体が「成功した」わけではありません。successの値を必ず確認し、失敗時の代替処理(デフォルト値を使う、通知を出す等)を書いてください。
  • 全ての処理をpcallで囲む必要はありません。むしろ普段は自然にエラーを出して気づける状態にしておき、「外部要因で失敗しうる処理」だけをpcallで保護するのが良い設計です。

補足

pcallの第2引数以降には、保護したい関数に渡す引数をそのまま続けて書けます(上記のpcall(json.decode, jsonString)のjsonString部分)。DB連携(Tier3)や外部API連携(Tier3-22)など、失敗しうる処理を扱うレッスンで今後も活用します。
